# 版本策略

## 问题

原型阶段就跑到 `0.3.0`，看起来像做了一大半，其实还在给自己用。版本号是给**别人**判断兼容性的信号，不是进度条；按提交涨号，涨的是噪声。

## 四条规则

1. **原型阶段冻结在主版本线内。** 现在这条线是 `0.3.x`。除非行为契约变了（见第 3 条），否则**只允许 patch 递增**，不再出现 `0.4`。
2. **不按提交升版本。** 每次改动写进 `CHANGELOG.md` 的 `## Unreleased`。只有打 checkpoint（进整合包、或明确说"这版可以给别人试"）时才封版，一次封版 = 一次 patch。
3. **minor 只给契约变更。** `0.4.0` 意味着"别人装的东西可能要多做一件事"：默认折叠名单变了、配置项改名、`tool_fold` 的 action 变了。加功能不算。
4. **1.0.0 只在 API 冻结之后。** 在那之前，任何"稳定版"的说法都不成立。

## 为什么给已发布的 0.1/0.2/0.3 重排

不能，也不该。这三个号已经推到公开仓库、整合包按 40 位 commit 钉过，重排等于让历史撒谎，下次有人对照 tag 会踩空。**能做的是改速率，不是改过去。**

## 怎么封版

```bash
node scripts/release.mjs           # 原型规则：只升 patch
node scripts/release.mjs --minor   # 契约变更，需在 CHANGELOG 里写明变更点
node scripts/release.mjs --dry-run # 只看结果，不写文件
```

脚本做三件事：把 `## Unreleased` 改名成新版本号、同步 `package.json`、打印整合包需要钉的 YAML 行（含完整 commit 与 blob 链接）。
